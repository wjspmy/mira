# Mira 已知未解决问题

> 更新日期：2026-07-09

## 1. 跨标签撤销会串到上一个文件内容

### 状态

未解决。

### 复现步骤

1. 打开文件 A。
2. 再打开文件 B。
3. 当前处于文件 B。
4. 按 `Ctrl+Z`。

### 现象

文件 B 的内容可能被撤销成文件 A 的内容。

### 影响

这是编辑器可信度问题。用户在多标签之间切换后，使用撤销操作可能破坏当前文件内容。

### 初步原因判断

当前多个标签复用同一个 Tiptap / ProseMirror editor 实例。切换文件时通过 `setContent()` 替换编辑器内容，但 ProseMirror history plugin 的 undo/redo 栈没有真正按文档隔离。

因此，切换文件后执行 undo 时，历史栈里仍可能保留上一个文件的 `setContent` 或编辑历史，导致当前文件回退到另一个文件的内容。

### 已尝试方案

曾尝试在加载文档后重建 `EditorState` 来清空 history：

```ts
editor.commands.setContent(md || "");
editor.view.updateState(EditorState.create({
  doc: editor.state.doc,
  schema: editor.schema,
  plugins: editor.state.plugins,
}));
```

该方案经手动测试未通过，已回退。

### 后续建议方案

优先考虑以下方向之一：

1. **每个标签维护独立 EditorState**
   - 切换标签时保存当前 tab 的 `EditorState`。
   - 切入另一个 tab 时恢复对应 `EditorState`。
   - 这样 undo/redo history 可以按 tab 隔离。

2. **每个标签维护独立 editor 实例**
   - 实现成本更高，但隔离最彻底。
   - 需要注意性能、组件生命周期、图片解析目录和 autosave 绑定。

3. **深入控制 ProseMirror history plugin**
   - 在程序化 `setContent` 时确保不进入 undo history。
   - 或在切换文档时可靠清空 history。
   - 需要验证 Tiptap 当前版本下的正确写法。

### 临时规避建议

在彻底修复前，多标签切换后不要立即依赖 `Ctrl+Z` 撤销历史。用户若触发该问题，应重新打开文件或从磁盘恢复最近保存内容。

## 2. 外部资源管理器重命名/移动文件的同步不完整

### 状态

未解决。

### 现象

如果用户在 Mira 外部，例如 Windows 资源管理器中，重命名或移动当前工作区中的文件/文件夹，Mira 的文件树、已打开标签、最近打开列表可能无法完整同步。

### 初步原因判断

当前文件监听主要处理 `create` / `delete` / `modify`，没有完整实现设计文档中的 `fs:moved { oldPath, newPath }` 语义。

外部 rename/move 通常会被底层 notify 表现为复杂事件组合，当前前端无法可靠知道旧路径和新路径之间的对应关系。

### 后续建议方案

1. Rust 后端增强 notify 事件识别，尽量发出明确的 move/rename 事件。
2. 前端收到 move/rename 后同步：
   - 文件树缓存；
   - 展开状态；
   - 已打开 tab 的 `filePath`；
   - 最近打开列表；
   - 当前编辑器图片解析目录。
3. 如果无法可靠识别 old/new path，则至少刷新相关父目录，并对已打开但路径消失的 tab 给出提示。

## 3. 窗口关闭 / 崩溃恢复对 dirty 文档保护不足

### 状态

未解决。

### 现象

当前关闭单个 tab 时会提示 dirty 文档，但窗口关闭、应用崩溃或异常退出时，对未保存内容的保护还不完整。

### 影响

对写作软件来说，这是重要可靠性问题。尤其是未命名文档或尚未自动保存完成的内容，存在丢失风险。

### 后续建议方案

1. 增加窗口关闭前 dirty 文档拦截。
2. 实现草稿恢复机制：
   - 定期保存未命名 / dirty 文档草稿；
   - 启动时检测未恢复草稿；
   - 提供恢复或丢弃选项。

## 4. 文本编码 / BOM / 行尾策略未完成

### 状态

未解决。

### 现象

当前后端文本读取仍以 UTF-8 为基础，未实现完整的编码探测、BOM 处理、GBK 回退和行尾风格保留。

### 影响

Windows 中文用户打开历史 Markdown 或其他编辑器保存的文件时，可能遇到读取失败或保存后行尾/编码变化。

### 后续建议方案

1. 读取时探测 UTF-8 BOM / UTF-8 / GBK 等常见编码。
2. 保存时尽量保留原文件编码和行尾风格。
3. 在无法识别编码时给出明确提示，而不是静默破坏文件。

## 5. 文件系统命令路径沙箱未完成

### 状态

未解决。

### 现象

当前 Tauri 后端文件操作命令直接接收前端传入路径。虽然 Mira 是本地单用户桌面应用，但发布前仍应补齐路径边界校验。

### 后续建议方案

1. 维护允许访问的根路径集合，例如当前工作区根目录、用户显式打开的文件所在目录。
2. Rust 端对传入路径做 `canonicalize`。
3. 确认目标路径位于允许根集合内。
4. 对删除、移动、重命名、写入等高风险操作优先加校验。
